# Lernquest – notes for Claude

German educational roguelike for primary-school children (grades 1 to 3). Read CONTRIBUTING.md first (structure, commands);
README.md is the general German page for parents.

## Always keep the changelog up to date

**Every change a player or parent can notice must get an entry in `CHANGELOG.md` in the same commit.**

- No version numbers – entries are grouped by date: `## JJJJ-MM-TT` (newest first, each date only once).
  Add to today's heading if it exists, otherwise create it at the top.
- Under the date use only these groups, in this order: `### Neu`, `### Verbessert`, `### Behoben`.
- One `- ` line per point: a short German sentence a child or parent understands
  (no technical terms like "localStorage", "Service Worker", "CI").
- **Keep it short – it's release notes for players, not a commit log.** Summarise what a player notices:
  at most about 3 points per group and 6 per day, each point one short sentence (roughly 15 words).
  Merge related changes into one point, mention only the most noticeable fixes and sum up the rest
  (e.g. „Viele kleine Text- und Anzeigefehler.“). Details belong in commit messages.
  Exception: a big release (like v2) gets one richer entry on its release date that lists every new theme and feature.
- The oldest entry (2026-11-07) is the go-live release note („Lernquest ist online!“). Leave it as it is;
  never add fixes or details to it.
- Purely internal changes (tests, CI, refactoring) don't need an entry.
- The file is shown in the game ("Was ist neu?" on the title screen): `tools/build.js` parses it, so keep the format
  exactly as described in the file header and run `npm run build` afterwards. The build fails if dates are out of order.

## Workflow

- Edit `src/*`, never `docs/index.html`, `docs/sw.js` or `docs/manifest.webmanifest` by hand – they are generated by
  `npm run build` and are not committed: CI builds them and deploys `docs/` to GitHub Pages on every push to `main`.
- Monster art: draw in `src/monsters.ts`; never edit `art/monsters/` by hand. `npm run build` (or `npm run svg`) bakes every
  variant to `art/monsters/raw/` and runs svgo only on changed ones (hashes in `art/monsters/manifest.json`) into
  `art/monsters/svg/`, which the game uses. Commit `art/` too. After changing the svgo settings run
  `node tools/svg_compare.js` (Playwright) to confirm the optimised SVGs look identical.
- Before committing, opening a pull request or merging: `npm run format && npm run lint && npm run typecheck && npm run build && npm test && npm run playtest && npm run e2e`
  (tests take about half a minute, the playtest about a minute, the browser tests under a minute; CI runs the same on every pull request and push to `main`).
- **Any change a player can see needs before/after screenshots and the owner's approval before it is committed
  to `main`.** Take screenshots of every affected screen (phone size, 390×844 at 2×) before and after the change
  (`npm run screenshots <dir>` shoots the screens listed in `tools/screens.js`, `npm run screenshots <before> <after>`
  lists the ones that changed; add a new screen to that list), publish them side by side as an artifact page, and wait for the go-ahead. Never push visual or copy changes
  to `main` unapproved; a branch is fine for work in progress.
- New units: see CONTRIBUTING.md „Adding a unit“. Never add a second list of units anywhere – everything reads `UNITS`
  (`src/units.ts`) and takes `grade` and `subject` from the unit itself.
- The game engine is `src/app/*.ts`: ES modules that import what they use; `src/main.ts` lists them in the order they
  start. What several of them change (`meta`, `run`, `mode` …) lives in `src/app/state.ts` as `state.meta` etc.
  Use the words in `GLOSSARY.md`; decisions that should not be re-argued are in `adr/`.
- A screen builds its markup with `html` (`src/ui/html.ts`, escapes what it is given; `raw()` for what is markup
  already; `String(flag)` for an attribute that must say "false") and passes it to `screen(markup, actions)`, a dialog
  to `modal(markup, actions)`; a tap on `data-action="name"` calls `actions.name`, and `on(actions)` adds actions for
  what a screen puts in later. No `onclick` after rendering. `src/app/feedback.ts` is the shortest example (`adr/0008`).
- A change that must not alter what a child sees is proven with the bot's recording: `TRACE_DIR=before npm run
  playtest` on the old state, the same with another folder on the new one, and the files must be identical.
- Anything a screen looks like follows „Design system“ below.
- Small symbols: emojis in the app's text are swapped for the drawn icons in `src/icons.ts` (key = the emoji) when shown.
  A new emoji needs a drawn icon there in the same style (see the file header), otherwise it shows as the device's emoji.
- Icons and iOS launch screens (`docs/icons/`, `docs/splash/`) come from `node tools/make_icons.js`
  (needs Playwright); only rerun it when the artwork changes.
- GitHub Pages is deployed by CI from `main`: https://thezieger.github.io/rogue-adventures/

## Design system

`docs/gallery.html` (built from `src/gallery.ts`) is the design system: every token with how often it is used, every
shared building block in each state, and the rule for using it. Look there before styling anything. Why: `adr/0009`.

- **Tokens only.** Every colour, size, space, line width, shadow, duration and font comes from
  `src/styles/tokens.css`, in stylesheets and in inline `style="…"` alike. Stylelint fails the rest.
- **Roles, not palette.** A rule takes a role (`--ink`, `--card`, `--gold` …) or a tone pair (`--good-tint` with
  `--good-ink`; also `bad`, `warn`, `hot`, `info`). A palette step (`--navy-600`) is only for drawings (coins, maps,
  the Turmwacht board). A see-through colour is a token (`--glass`, `--shade` …) or `color-mix()` of a role.
- **The scales are closed:** 9 text sizes, 4 line heights, 5 radii, 8 spaces, 3 line widths, 2 tap sizes
  (`--tap` 44 px is the smallest thing a child taps), 7 durations, 35 palette colours. Need a value between two
  steps? Take the nearer step. A new step or colour changes `tests/test_design.js` and needs the owner's yes.
- **One building block per job.** Before writing a class, find the job in the gallery:
  `btn` (+ `secondary`, `ghost`, `danger`, `small`; one gold button per screen), `pill` (a label that marks a state,
  tones `new good warn hot bad info`, size `lg`; never tapped), `chip` (one choice among a few, chosen is gold),
  `switch` (on/off, parents only), `callout` (one line of advice), `bar` (+ `hp`, `xp`), `card`, `choice`, `modal`,
  `tut`/`speak` (round helpers). A new look for an existing job is a variant of that block, not a new class.
- **A new block** gets a specimen with its rule in `src/gallery.ts` and its name in `BLOCKS` in
  `tests/test_design.js`. A new state of a block gets a specimen too.
- A disabled control is designed (flat and grey), never just faded. Selection is the gold ring (`--ring`), the field
  being typed in is blue (`--ring-focus`); green and red appear only after an answer.
- Exceptions, on purpose: inside the Turmwacht board lengths are board units (`--u`); the fight choreography of
  Turmwacht and Kreisel keeps its own animation times (tuned to the sounds). Transitions always use `--t-*`.
- Patrick Hand (`--font-hand`) for headings, names and feedback, Andika (`--font-body`) for everything read or
  calculated, weights 400 and 700 only. What not to drift back into: `tools/unslop-visual.md`.

## Code style

- **Lazy senior dev:** the least code that solves the problem cleanly. Apply SOLID and the usual patterns only where
  they pay off; if the cheap solution is fine long-term, take it. No speculative abstractions, no dead code.
- **Comments: only the essential ones.** Comment a non-obvious *why* (a game rule, a save invariant, a browser quirk),
  never what the code already says. No banners, no narration, no change history in comments. Keep it that way when editing.

## Saves must never break

- Players' saved progress and running adventures must keep loading after every change – always backwards compatible.
- Never rename or repurpose storage keys or saved fields; add new fields with defaults, map old values to new ones
  (see `RENAMES` and the defensive loading in `src/app/storage.ts`), and cover save changes in `tests/test_storage.js`.

## Conventions

- **English for everything developers read:** code, comments, commit messages, pull requests, ADRs, `CONTRIBUTING.md`.
  German only for what a child or parent reads (app text, learning content, `CHANGELOG.md`, `README.md`, issue
  templates), for the curriculum notes in `lehrplan/`, and for the product's own names from `GLOSSARY.md`.
  `README.md` stays general: no file names, commands or code – those go into `CONTRIBUTING.md`.
- All player-facing text is German, child-friendly, with German typography („…“, –).
  Check new names and messages against `tools/unslop-text.md` (patterns to avoid).
- Lernquest is about learning, not gaming: player- and parent-facing copy talks about learning, practising and
  getting going, not about playing. Say „loslegen“, „weitermachen“, „üben“, „Thema“ (one unit such as Zahlenquest),
  „Abenteuer“ (one run), never „spielen“, „Spiel“ or „Spiele“ for what the child does in Lernquest
  (e.g. „Jetzt loslegen“, not „Jetzt spielen“; „3 Themen“, not „3 Spiele“). „Spielstand“ stays as the usual word for
  the save. Learning content about real-life play (Fußball spielen, Spielplatz) is fine.
- No time pressure. Children see whole numbers; the only comma numbers are money and lengths, written as the
  curriculum asks (1,50 €; 1,20 m).
- No external requests at runtime (fonts are self-hosted in `docs/fonts/`), no tracking, everything stays on the device.
  Only exception: the feedback screen posts the message to the Google Form when the player taps „Absenden“.
- The app is an installable PWA: assets the game needs offline must be listed in `CORE` in `src/sw.js`.
- Learning content follows the class worksheets – check factual changes to `src/knowledge.ts` carefully.
- Never claim human expertise that didn't happen: content checks by AI agents are not „Lehrkräfte“, „Fachleute“ or
  „geprüft von Experten“. Changelog, README, docs, parent texts and PR texts say what was done, not who supposedly did it.
